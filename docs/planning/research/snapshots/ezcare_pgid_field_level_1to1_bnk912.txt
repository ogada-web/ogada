### §2-1 · RFID_tagId 아키텍처 비교 [DIFF · 판단 필요]

- **이지케어**: 수급자 마스터에 `RFID_tagId` **1 필드** 저장 → 수급자 태그 = 방문지(client 댁내) 태그 = 요양보호사 방문 인증 = 방문요양 워크플로 표준(공단 RFID태그 내역 vs 공단계획 비교 후 확정).
- **ogada**: 수급자 마스터에 rfidTagId 없음 → visit-event(`VisitRfid*`) 에서 `RfidTransmissionExcelParser` + `VisitRfidDiffMatcher` 로 **NHIS import ↔ 실 태그 이벤트** 매칭(엑셀 다운로드·서명 검증·`VisitRfidDispatchCandidateResponse`).
- **판정**: 두 아키텍처는 **동일 문제(방문 인증)를 다르게 해결**. ezcare 는 static tag ID를 client 에 pin, ogada 는 dynamic tag event를 매칭. 
  - ezcare 방식 = 태그 재발급 시 대량 update 필요, 데이터 노출 위험(RFID_tagId 평문 저장「가정」).
  - ogada 방식 = 태그 유연 배정, 감사 로그 자연 스러움, 하지만 client-level RFID 조회 API 부재.
- **planner 액션**: 재가(방문요양) 지원 확장 시 (P3) — Client 엔티티에 optional `rfidTagId` 필드 도입 검토. 지금은 daycare-first 로 NOT-GAP.
